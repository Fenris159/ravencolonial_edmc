# BGS-Tally colonisation settings relevant to RavenColonial EDMC

Researched 2026-09-27 against BGS-Tally `develop` commit [`a4b7bde`](https://github.com/aussig/BGS-Tally/commit/a4b7bde0c79001f16a27739ba1385d67e8f49171). BGS-Tally's [first-party colonisation guide](https://github.com/aussig/BGS-Tally/wiki/Usage-%E2%80%90-Colonisation-Tracking#customization) describes the user-facing behavior; the linked source lines below establish the current implementation.

Implementation update: the Ravencolonial settings tab now offers **Overlay Format** with **Breakdown** (existing columns) and **Simplified** (one Purchase column). Simplified uses the main-tab carrier picker and follows the purchase/unknown-state rules below. The additional selectable BGS-Tally metrics remain recommendations for a later change.

## What the reported three amounts mean

The report is about **selecting what quantity a column represents**, chiefly in BGS-Tally's colonisation progress panel **inside the main EDMC window**. It has a commodity-name column and **three quantity slots**. Each quantity slot can be set to **Required**, **Delivered**, **Remaining**, **Purchase**, **Cargo**, or **Carrier**. The current source opens a choice menu on a quantity header's left click and changes units (tonnes or ship loads) on right click. The guide says left clicking cycles through choices; that detail appears out of date relative to the current source. The choices are [defined here](https://github.com/aussig/BGS-Tally/blob/a4b7bde0c79001f16a27739ba1385d67e8f49171/bgstally/windows/progress.py#L81-L151) and the [header event binding and menu](https://github.com/aussig/BGS-Tally/blob/a4b7bde0c79001f16a27739ba1385d67e8f49171/bgstally/windows/progress.py#L338-L350), [menu actions](https://github.com/aussig/BGS-Tally/blob/a4b7bde0c79001f16a27739ba1385d67e8f49171/bgstally/windows/progress.py#L600-L642), and [units toggle](https://github.com/aussig/BGS-Tally/blob/a4b7bde0c79001f16a27739ba1385d67e8f49171/bgstally/windows/progress.py#L588-L596) are in the panel code. It saves the selected quantity columns, units, view, and carrier modes in `colonisation.json` ([save](https://github.com/aussig/BGS-Tally/blob/a4b7bde0c79001f16a27739ba1385d67e8f49171/bgstally/colonisation.py#L1194-L1208), [load](https://github.com/aussig/BGS-Tally/blob/a4b7bde0c79001f16a27739ba1385d67e8f49171/bgstally/colonisation.py#L1264-L1277)).

| BGS-Tally label | Meaning in its code | Closest current RavenColonial EDMC display |
| --- | --- | --- |
| **Required** | Original total required | No exact overlay metric; **Need** is remaining need. |
| **Delivered** | Required minus remaining | No separate column. |
| **Remaining** | `max(0, required - delivered)` | **Need**. |
| **Purchase** | `max(0, required - delivered - ship cargo - personal carrier cargo)` | No equivalent; current **FC's** is a signed carrier surplus/deficit. |
| **Cargo** | Current ship hold | **Ship**. |
| **Carrier** | Amount physically held in the personal carrier's cargo | No equivalent; current **FC's** shows `FC stock - need`. |

BGS-Tally's exact arithmetic is in [`Commodity.__post_init__`](https://github.com/aussig/BGS-Tally/blob/a4b7bde0c79001f16a27739ba1385d67e8f49171/bgstally/windows/progress.py#L53-L68). **Purchase** is an amount still to acquire, rather than stock or a market buy order. The first-party guide [defines it the same way](https://github.com/aussig/BGS-Tally/wiki/Usage-%E2%80%90-Colonisation-Tracking#customization). Its **Carrier** choice has another layer: for a selected carrier, **Buy**, **Sell**, and **Cargo** mean demand/buy order, stock offered for sale, and held cargo respectively ([menu and tooltips](https://github.com/aussig/BGS-Tally/blob/a4b7bde0c79001f16a27739ba1385d67e8f49171/bgstally/windows/progress.py#L600-L680)). These are distinct from the **Purchase** progress metric.

The in-game BGS-Tally overlay is **not the three-column panel**: [`overlay_text()`](https://github.com/aussig/BGS-Tally/blob/a4b7bde0c79001f16a27739ba1385d67e8f49171/bgstally/windows/progress.py#L507-L555) outputs the name, progress, and **only quantity slot 1** plus total. Thus changing the first panel slot changes which metric appears on the overlay; changing slots 2 or 3 does not. BGS-Tally [passes this text to its colonisation overlay](https://github.com/aussig/BGS-Tally/blob/a4b7bde0c79001f16a27739ba1385d67e8f49171/bgstally/ui.py#L469-L477).

## Current plugin and port recommendations

RavenColonial EDMC's [overlay guide](OVERLAY.md#data-shown) and [`render_layers.py`](../overlay/render_layers.py) show fixed **Need** (remaining), **Ship**, and optional **FC's** (signed `FC stock - remaining need`). Its carrier picker selects **All** project-linked carriers or one callsign; it changes which stock feeds the signed FC column, not which quantity metric the column represents ([selection and delta calculation](../overlay/build_project.py)). The same layout is used in its HUD and popout ([guide](OVERLAY.md#requirements)). Its **Track All** mode sums remaining need across active builds and deduplicates linked carriers ([guide](OVERLAY.md#track-all)).

1. **Add metric selection to the existing tracker first.** Offer a compact control in the Ravencolonial tab that chooses each visible numeric slot's metric, while keeping today's `Need / Ship / FC's` layout as the default. At minimum expose **Remaining**, **Ship cargo**, **Carrier cargo**, and **Purchase**; **Required** and **Delivered** need trustworthy original/depot totals, so make them available only when those values exist. Store stable metric IDs rather than translated labels. Drive both HUD and popout through the same selected-metric rendering path. This ports the useful behavior without replacing the existing carrier picker.
2. **Keep carrier identity and metric independent.** The existing All/one-carrier picker should choose the cargo source for both **Carrier cargo** and **Purchase**. Label the existing signed **FC surplus/deficit** explicitly as its own metric so users cannot mistake it for BGS-Tally's physical **Carrier** amount. Avoid interpreting RavenColonial aggregate cargo as an individual carrier. If a manifest has not synced, display an unknown/sync value instead of zero, as the current FC display does ([guide](OVERLAY.md#use)).
3. **Define Purchase carefully.** For each commodity, calculate `max(0, remaining_need - ship_hold - selected_carrier_hold)`, using one ship hold and the currently chosen carrier source. For **Track All**, aggregate the needs first and subtract ship/carrier cargo **once per commodity**; subtracting them separately for each build would understate the purchase amount. Clamp at zero. If a selected manifest is unknown, Purchase is unknown too, rather than a misleading exact number. BGS-Tally's formula is a model, but these aggregate and unknown-state rules are RavenColonial-specific implementation recommendations.
4. **Consider the other small controls separately.** BGS-Tally supports full/reduced/minimal/none commodity views ([enum](https://github.com/aussig/BGS-Tally/blob/a4b7bde0c79001f16a27739ba1385d67e8f49171/bgstally/constants.py#L203-L207), [row filter](https://github.com/aussig/BGS-Tally/blob/a4b7bde0c79001f16a27739ba1385d67e8f49171/bgstally/windows/progress.py#L817-L853)); tonnes/ship-load units ([formatter](https://github.com/aussig/BGS-Tally/blob/a4b7bde0c79001f16a27739ba1385d67e8f49171/bgstally/windows/progress.py#L1044-L1061)); quantity/category/alphabetical sorting ([guide](https://github.com/aussig/BGS-Tally/wiki/Usage-%E2%80%90-Colonisation-Tracking#customization)); and a configurable row cap or scrollable panel ([guide](https://github.com/aussig/BGS-Tally/wiki/Usage-%E2%80%90-Colonisation-Tracking#progress)). RavenColonial already hides zero-need rows and groups by category ([guide](OVERLAY.md#data-shown)). A **Purchase > 0** row filter and a per-column tonnes/trips display are the most relevant follow-ons for hauling; a scroll option makes more sense in the popout than the in-game HUD.

### Data boundary

RavenColonial's project `commodities` are **remaining need**, synchronized from `ColonisationConstructionDepot`, and `maxNeed` is a total; [the local API reference](RavenColonial_API_Reference.md#construction-remaining-need-vs-delivery-history) describes that contract. For **Required** and **Delivered**, derive per-commodity values from a valid depot `ResourcesRequired` snapshot (`RequiredAmount` and `ProvidedAmount`) where present. Do not infer per-commodity original totals from a project-wide `maxNeed`, or from a need that has already decreased. Current ship cargo and selected FC manifest can provide **Cargo**, **Carrier**, and **Purchase** without changing server project state.
